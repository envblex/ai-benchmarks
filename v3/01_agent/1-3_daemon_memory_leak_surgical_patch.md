# 問1-3：常駐データコレクターデーモンの周期的OOMクラッシュ調査とメモリリークの外科手術

## 1. 課題設定
本番バックグラウンドでIoTストリームデータをポーリング・変換するPython製デーモン（`/workspace/collector/`）が、起動後約3分でRSS（物理メモリ使用量）が肥大化し、cgroupsにより強制終了（OOM Kill）される。
ソースコード内に明示的な原因コメントやヒントは存在しない。
エージェントはメモリプロファイリング（`tracemalloc`, `gc`, `objgraph` 等の手法）またはコード解析を行い、オブジェクト参照の解放漏れ箇所をピンポイントで特定・修復せよ。

## 2. 作業環境
- リポジトリ: `/workspace/collector/`
- 再現スクリプト: `python3 tests/reproduce_leak.py`

## 3. 達成条件
1. 再現スクリプトを実行し、10,000メッセージ処理ごとのメモリ成長プロファイルを確認すること。
2. 循環参照やグローバルリスナー、未クローズの接続プール等、メモリ保持の原因となっている箇所を修正すること。
3. コードの本来のポーリングスループット（1,000 msg/sec以上）を損なわずに、10万メッセージ処理後のメモリ増加量を5MB未満に抑制すること。

## 4. 採点基準（20点満点）
* **6点**：メモリプロファイルまたは静的解析により、リークを引き起こしている参照保持箇所を正確に特定している。
* **8点**：修正パッチを適用し、デーモンの機能（正常系・異常系リトライ）を壊すことなく修正を完了している。
* **6点**：10分間の連続高負荷HoldoutストレステストでRSSが50MB以下で平坦に推移し、OOMを起こさない。
