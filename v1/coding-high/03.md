# 問3-3: ゼロダウンタイム・スキーママイグレーションのための双方向互換レイヤー

**カテゴリ**: コーディング性 (高レイヤー)  
**配点**: 20点

## 課題設定

稼働中の EC システムにおいて、データモデルを

- V1: 1 つの注文につき 1 つの配送先住所と単一の決済手段のみを持つフラットな構造
- V2: 1 つの注文を複数の配送パッケージに分割でき、かつ複数の決済手段 (ポイント + クレジットカード等) を組み合わせられる構造

へ **無停止** で移行したい。ローリングアップデート中、V1 のコードで動く旧サーバーと V2 のコードで動く新サーバーが同じデータベース (またはドキュメントストア) に対して同時に読み書きを行う。

この期間中にデータの欠損・破壊を起こさないための **双方向データ変換・永続化アダプタ** を実装せよ。

## 制約条件

1. V2 サーバーが「複数配送先・複数決済」の注文データを保存した後、V1 サーバーがその注文を読み取ってステータス (例: 注文備考欄) だけを更新して再保存しても、V2 固有の情報 (2 つ目以降の配送先や決済内訳) が消滅・上書きされないこと (Unknown Fields / Extension data の保持機構)。
2. V1 サーバーが書き込んだデータが V2 サーバーから読み取られた際、正規の V2 スキーマ (要素数 1 の配列構造) へ透過的に変換されること。
3. V1 と V2 の両方に存在するフィールド (例えば金額の合計値) が V1 側で更新された場合、V2 側で読み取った際に古い V2 データとの不整合を検知し、定義された解決ルールに従ってマージされること。

## 採点基準 (20点)

- **10点**: V2 で作成 → V1 で読み取り・一部更新して保存 → V2 で再読み取り、という往復 (Round-trip) テストにおいて、V2 固有の構造データが 1 ビットも失われずに復元される。
- **5点**: V1 で金額変更が行われた後、V2 で読み取った際に決済内訳の合計値と注文総額の不整合が正確に検知・補正される。
- **5点**: 変換ロジックが純粋なアダプタ層に閉じ込められており、V2 のコアドメインロジック内に V1 のレガシーフィールドへの直接参照が漏出していない。
