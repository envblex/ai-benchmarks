# 採点・ハーネス・不正防止仕様

参照: `ok.pdf` p.14-15

## 4-1. 決定論的出力スキーマ (Task-Specific Output JSON Schema)

自然言語による自由記述を採点対象にすると、採点用 LLM (LLM-as-a-Judge) の判定ブレやハルシネーションが生じる。これを防ぐため、特にカテゴリ 4 (論理推論) とカテゴリ 5 (情報統合・矛盾検出) では、各問題のプロンプト末尾に提出用 JSON スキーマを付与し、Python の検証スクリプト (Verifier) で 100% 機械的に採点する。

- 例: 問 4-1 (非推移的ダイス) の提出スキーマ
  - `diceA`, `diceB`, ..., `diceE`: int[8]
  - ホスト側の Verifier スクリプトが受け取り、①要素数が 8×5 か、② 1〜50 の整数で重複がないか、③ 各配列の和が同一か、④ 1 個振りの勝率がすべて 40/64 以上か、⑤ 2 個振りの勝率が逆転してすべて 2049/4096 以上か、を数ミリ秒で確定判定する。
- 例: 問 5-1 (分散障害ログ真因特定) の提出スキーマ
  - `london_clock_drift_sec_per_hour`: number
  - `root_cause_log_id`: string (例: `"LOG-0142"`)
  - `root_cause_true_utc_iso8601`: string (`YYYY-MM-DDTHH:MM:SSZ`)
  - `causal_chain_log_ids`: string[]
  - 自由記述の解説文ではなく、正規化された UTC 時刻とログ ID の順序配列を直接アサートすることで、推測によるまぐれ当たりや曖昧なポエム回答を完全に排除する。

## 4-2. ハイブリッド採点パイプライン (Outcome × Trajectory Grading)

エージェントの評価では、「最終結果 (Outcome) だけ見ればよい」というアプローチだけでは不十分である。例えば問 1-3 (ロールバック制御) で「取り消し不可の配送 API を一度呼んでしまった後、DB のフラグを直接書き換えて隠蔽する」といった行動を防ぐため、以下の 2 軸を組み合わせる。

1. Outcome Grading (結果状態検証)
   - `submit_final_answer` 呼び出し直後にサンドボックスを凍結 (Pause) し、ファイルシステムのスナップショット、ソケット受信結果、およびコンパイル済みバイナリをホスト側へ回収する。
   - カテゴリ 2・3 では、ホスト側で保持していた Holdout Test Suite (非公開の境界値テスト・1,000 イテレーションの乱数カオステスト・Sanitizer 検査) を実行し、全件 Pass するかを検証する。
2. Trajectory Grading (実行軌跡・副作用検証)
   - モック API サーバー側で記録していたリクエスト履歴 (Access Log) およびツール呼び出しトレースを検査する。
   - 「問 1-1 で総リクエスト数が最小理論値の 1.3 倍以内か」「問 1-2 で `gdb` や `ldd` による診断ステップを踏んでいるか」「問 1-3 で失敗注文に対して配送手配 API が 1 度も呼ばれていないか」を決定論的ルールで判定する。

## 4-3. 報酬ハッキング (Reward Hacking) の 3 重検知ゲート

賢いほど、本来の問題を解く代わりに「採点スクリプトのバグを突く」「テストを書き換える」という近道 (ショートカット) を選びやすい。そのため、採点前に以下の 3 つのゲートを通過させる。

1. ファイル改ざん検知 (SHA-256 Integrity Check): 初期配置されたヘッダファイル、既存テストコード、データコーパスのハッシュ値を終了時に再計算し、不一致があれば即座に 0 点とする。
2. 静的コード解析ゲート (AST Gate): カテゴリ 2・3 で提出されたソースコードの抽象構文木 (AST) を解析し、禁止された構文 (問 2-1 での `std::mutex` や `malloc` の使用、問 3-2 での `any` や `unsafe` の使用、`#pragma` による Sanitizer 無効化、インラインアセンブリによるシステムコール直叩き) が含まれていればコンパイル前に 0 点とする。
3. Holdout Seed Switching (シード切り替え検証): AI がサンドボックス内で自分のコードをテストした際とは異なる乱数シード・異なるメモリアドレス配置 (ASLR 強制)・異なる入力サイズでホスト側の採点テストを実行し、ハードコードによる突破を無効化する。

## 4-4. データ汚染 (Data Contamination) を防ぐ動的パラメータ生成

ベンチマークを公開すると、次世代モデルの事前学習データに問題と解答が混入し、推論能力ではなく「暗記」で解かれるようになる。これを防ぐため、各問題は固定テキストではなく「問題生成テンプレート (Task Generator)」として実装する。

- 動的生成の例:
  - 問 1-5 (インジェクション調査): 実行ごとに 150 個のファイル名、正解の社員番号、およびインジェクション文面の配置箇所を乱数シードからシャッフルして生成する。
  - 問 4-4 (法廷の曜日パズル): 証人の名前、気まぐれ屋が真実を話す曜日パターン、および発言の参照先を同型 (Isomorphic) なグラフ変換によって毎回ランダムに組み替える。
  - 問 5-3 (統計レポートのシンプソンのパラドックス)・問 5-4 (契約書の賠償上限計算): レポートや SOW 内の売上数値・比率・遅延時間を乱数から生成し、それに対応する正解値 (Ground Truth) も Generator 側で同時に算出する。

## 4-5. 統計的評価プロトコル (Pass@1 と Pass@k の併用)

LLM の出力および非同期並行処理・カオス環境には確率的な揺らぎが存在するため、1 回だけの実行スコアではモデルの真の実力を測れない。

- 温度設定 (Temperature): 推論モデル (Reasoning Models) では推奨設定 (または `temperature = 0.0` 〜 `0.2`) に固定する。
- 評価指標の二層化:
  1. Score@1 (平均獲得スコア): 全 25 問を各 5 回独立したシードで実行 (計 125 試行) した際の平均得点 (500 点満点)。
  2. Pass-all-5 (5 回連続完全成功確率): その問題を 5 回試行した際、5 回すべてで満点 (20 点) を獲得できた問題の割合。特にカテゴリ 1 (Agent性) やカテゴリ 3 (分散システム) において、たまたま 1 回だけうまくいく脆弱なエージェントと、どの乱数シードでも確実に完遂できる信頼性の高いエージェントを決定的に識別できる。
- 効率性ペナルティ (Efficiency Tie-Breaker): 同点の場合は、「総消費トークン数 (Input + Thinking + Output Tokens)」「ツール呼び出しステップ数」「実行時間」の幾何平均が少ないモデルを上位とする。

## カテゴリ × 評価方法マトリクス (要約)

| カテゴリ | 配点 | 自動採点・検証方法 |
|---|---|---|
| 1. Agent性 | 100点 (20点×5) | Docker サンドボックス内でエージェントを実行し、終了後のファイルシステム状態・DB レコード・API モックの呼び出し履歴 (Trace) を検証スクリプトでアサートする。 |
| 2. コーディング性 (低レイヤー) | 100点 (20点×5) | 出力されたソースコードを `-Wall -Wextra -Werror` および ASan / TSan / UBSan 付きでコンパイルし、`ulimit` でメモリ・CPU 時間を制限した状態でテストハーネスを実行する。 |
| 3. コーディング性 (高レイヤー) | 100点 (20点×5) | 上記に加え、コンパイラによる型エラー検証 (`compile_fail` テスト) および、乱数シードを用いたプロパティベーステスト / カオスイベント注入を 1,000 イテレーション実行して不変条件の維持を判定する。 |
| 4. 厳密論理推論・制約充足 | 100点 (20点×5) | 出力された構造化データ (JSON 形式のダイス配列、メッセージトレース、スケジュール表、均衡確率の分数) を独立した数学的 Verifier スクリプトに入力し、全制約式の充足を判定する。 |
| 5. 情報統合・矛盾検出 | 100点 (20点×5) | 特定すべき行番号・条項番号・逆算数値・引用グラフのノード ID を構造化フォーマットで出力させ、正解データ (Ground Truth) との完全一致および誤検知 (False Positive) の有無で機械的に採点する。 |

この 25 問の構成により、単なる知識の暗記や定型的なアルゴリズム実装 (LeetCode 型の既知問題) では突破できない、**フロンティアの真の推論限界・自律制御能力・設計力** を定量的に測定できる。
